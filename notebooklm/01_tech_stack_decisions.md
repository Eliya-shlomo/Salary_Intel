# החלטות טכנולוגיות — כל טכנולוגיה, למה היא, ומה החלופות (מסמך 01)

> לכל טכנולוגיה: **מה זה** → **למה בחרתי** → **מה החלופות** → **מה הייתי משנה** → **שאלת ראיון צפויה**.
> זה המסמך שהכי חשוב לשלוט בו. מראיין ישאל "למה X ולא Y" כמעט על כל שורה בסטאק.

## חלק א' — Backend Core

### 1. FastAPI

**מה זה:** פריימוורק web ל-Python, async-native, מבוסס Starlette (ASGI) + Pydantic.

**למה בחרתי:**
- הצינור שלי הוא **I/O-bound**, לא CPU-bound. כמעט כל הזמן הוא המתנה ל-OpenAI ול-Postgres. async מאפשר לשרת אחד לטפל בעשרות בקשות במקביל בזמן ההמתנה.
- Pydantic מובנה — `QueryRequest`/`QueryResponse` נותנים ולידציה + סריאליזציה + תיעוד בחינם.
- מערכת ה-Dependency Injection (`Depends`) — כך מימשתי את `verify_api_key` כתלות שרצה לפני כל endpoint מוגן, בלי לשכפל קוד.
- Swagger אוטומטי ב-`/docs`.

**חלופות שנשקלו:**

| חלופה | למה לא |
|---|---|
| **Flask** | WSGI סינכרוני. כל בקשה חוסמת thread. עם המתנה של 5 שניות ל-OpenAI זה אסון תפוקה. גם צריך extensions לכל דבר (ולידציה, docs). |
| **Django / DRF** | כבד מדי. ORM, admin, auth, migrations — 90% ממנו מיותר ל-API עם 3 endpoints. Django async עדיין חלקי. |
| **Node.js / Express** | הייתי מאבד את המערכת האקולוגית של Python ל-ML: `openai`, `pgvector`, numpy. הצינור עצמו הוא Python-first. |

**שאלת ראיון:** *"אם הקוד שלך async, למה `SessionLocal` הוא סינכרוני?"*
**תשובה:** זו פשרה מודעת. SQLAlchemy הסינכרוני חוסם את ה-event loop בזמן שאילתת ה-DB. בקנה המידה הנוכחי (מסד קטן, שאילתה של מילישניות) זה זניח מול 2-3 שניות ההמתנה ל-OpenAI. בפרודקשן אמיתי הייתי עובר ל-`asyncpg` + `AsyncSession`, או לפחות מריץ את קריאות ה-DB ב-`run_in_threadpool`.

### 2. PostgreSQL + pgvector

**מה זה:** Postgres רגיל + extension שמוסיף טיפוס `vector` ואופרטורים למרחק (`<=>` קוסינוס, `<->` L2, `<#>` inner product).

**למה בחרתי:**
- **מסד אחד לשני סוגי דאטה.** לפוסט שכר יש גם שדות רלציוניים (`salary`, `role`, `years_experience`) וגם וקטור. עם vector DB נפרד הייתי צריך לסנכרן שני מסדים ולסבול מ-dual-write inconsistency.
- **החיפוש ההיברידי שלי הוא שאילתת SQL אחת.** ה-CTE-ים `semantic` + `keyword` + `rrf` רצים בתוך המנוע. עם Pinecone הייתי צריך: שאילתה ל-Pinecone → מביא IDs → שאילתה ל-Postgres → מאחד ב-Python. יותר round-trips, יותר latency, יותר קוד.
- **טרנזקציות.** `INSERT` של פוסט + הוקטור שלו הוא אטומי.
- **עלות תפעולית.** אין שירות נוסף לתחזק, לנטר ולשלם עליו.

**חלופות שנשקלו:**

| חלופה | למה לא |
|---|---|
| **Pinecone** | managed, מהיר בקנה מידה של מיליונים, אבל: עלות חודשית, dual-write, ו-metadata filtering חלש יותר מ-SQL מלא. בקנה מידה של אלפי פוסטים זה over-engineering. |
| **Weaviate / Qdrant** | חזקים, hybrid search מובנה, אבל שירות נוסף ב-docker-compose ועוד עקומת למידה. Qdrant הוא הכי מפתה מבין השלושה אם אגדל. |
| **Chroma** | מצוין לפרוטוטייפ, אבל לא בנוי לפרודקשן multi-user. |
| **Elasticsearch** | מעולה ל-BM25 + hybrid, אבל JVM כבד ותפעול לא טריוויאלי. |

**שאלת ראיון:** *"מתי pgvector כבר לא יספיק?"*
**תשובה:** כשמספר הווקטורים יגיע לסדר גודל של מיליונים והשאילתה תדרוש אינדקס ANN עם recall גבוה. כרגע **אין לי אינדקס וקטורי בכלל** — כל שאילתה עושה סריקה מלאה (exact KNN). זה בסדר עד עשרות אלפי שורות ואפילו מדויק ב-100%, אבל הצעד הבא הוא `CREATE INDEX ... USING hnsw (embedding vector_cosine_ops)`. מעבר לזה — Qdrant או pgvector עם sharding.

**שאלת ראיון:** *"מה זה `<=>`?"*
**תשובה:** אופרטור cosine **distance** של pgvector. לכן בקוד יש `1 - (embedding <=> query)` — כדי להפוך מרחק ל-similarity בטווח שבו 1 = זהה. וב-`ORDER BY` אני ממיין לפי המרחק עצמו בסדר עולה, כי מרחק קטן = דומה יותר.

### 3. OpenAI `text-embedding-3-small`

**מה זה:** מודל embedding, 1536 מימדים, רב-לשוני.

**למה בחרתי:**
- **עברית.** זו הדרישה החוסמת. רוב מודלי ה-embedding הפתוחים חלשים בעברית או לא תומכים בה בכלל.
- **cross-lingual.** השאלה מגיעה בעברית ("מפתח פרונטאנד") והפוסטים מכילים גם אנגלית ("Frontend Developer"). המודל ממפה את שניהם לאזור דומה במרחב הווקטורי — זה קריטי למערכת דו-לשונית.
- **עלות.** ~$0.02 ל-1M טוקנים. זניח.
- אין GPU לתחזק.

**חלופות שנשקלו:**

| חלופה | למה לא |
|---|---|
| **`text-embedding-3-large`** (3072 מימדים) | איכות מעט טובה יותר, אבל פי 2 אחסון, חיפוש איטי יותר, ופי ~6.5 בעלות. לא הוכחתי שהאיכות הנוספת שווה — וזה בדיוק סוג הדבר שהייתי בודק ב-ablation. |
| **`text-embedding-ada-002`** | הדור הקודם. נחות ב-benchmarks ולא זול יותר. |
| **Sentence-Transformers מקומי** (למשל `multilingual-e5`) | בחינם ופרטי, אבל: עברית חלשה יותר, צריך להריץ ולתחזק inference, ו-cold start בקונטיינר. שקול אם היה חשש פרטיות או נפח ענק. |
| **AlephBERT / HeBERT** (מודלים עבריים) | מותאמים לעברית אבל לא מאומנים ל-sentence similarity, ולא cross-lingual — היו נשברים על המונחים באנגלית. |

**שאלת ראיון:** *"למה 1536 מימדים? מה זה אומר?"*
**תשובה:** זו הרזולוציה של המרחב הסמנטי שהמודל מייצר. יותר מימדים = יותר ניואנס אבל יותר אחסון וחישוב. `text-embedding-3` תומך ב-`dimensions` parameter לקיצור (Matryoshka embeddings) — אפשר לרדת ל-512 ולחסוך, במחיר איכות. לא ניצלתי את זה.

### 4. `gpt-4o-mini`

**מה זה:** המודל הקטן והזול של OpenAI. משמש אצלי ב-**ארבעה** מקומות: extraction, query expansion, reranking, generation.

**למה בחרתי:**
- **עלות.** $0.15/$0.60 ל-1M טוקנים. שאילתה שלמה עולה ~$0.000085. עם gpt-4o זה היה פי ~20.
- **מהירות.** יש לי 2 קריאות סדרתיות בצינור הבקשה. מודל איטי היה מכפיל את ה-latency.
- **עברית טובה מספיק.** בדקתי בפועל — התשובות קוהרנטיות.
- המשימות שלי הן **extraction וסיכום**, לא הסקה מורכבת. זה בדיוק מה שמודל קטן עושה טוב.

**חלופות שנשקלו:**

| חלופה | למה לא |
|---|---|
| **gpt-4o / gpt-4.1** | איכות טובה יותר בניואנסים, אבל יקר ואיטי משמעותית. שקול לשלב ה-generation בלבד אם איכות התשובה הייתה נכשלת — היא לא. |
| **Claude Haiku** | חלופה אמיתית וטובה, עברית מצוינת. הייתי צריך client נוסף. שווה כ-fallback provider. |
| **Llama / Mistral מקומי** | בחינם ופרטי, אבל עברית חלשה משמעותית והרצה דורשת GPU. |

**שאלת ראיון:** *"אתה משתמש באותו מודל לארבע משימות שונות. זו הבחירה הנכונה?"*
**תשובה:** זו בחירה מודעת לפשטות. אבל המשימות באמת שונות באופיין: extraction ו-expansion הן משימות **מבניות** (JSON) שאפילו מודל קטן יותר יכול לבצע; generation היא משימה **יצירתית** בעברית שהייתה מרוויחה ממודל גדול יותר. הצעד הנכון הוא למדוד: להריץ ablation שמחליף רק את מודל ה-generation ולראות אם איכות התשובה משתפרת מספיק כדי להצדיק פי 20 בעלות.

### 5. Redis (דרך slowapi)

**מה זה:** in-memory key-value store. אצלי — אך ורק כאחסון מוני ה-rate limiting.

**למה בחרתי:**
- **rate limiting חייב להיות משותף בין תהליכים.** אם המונה יושב בזיכרון של התהליך, אז ב-4 workers של uvicorn מגבלה של 10/דקה הופכת בפועל ל-40/דקה. Redis הוא מקור אמת יחיד.
- אטומיות של `INCR` — אין race condition בין בקשות מקבילות.
- TTL מובנה — החלונות מתפוגגים לבד.

**חלופות שנשקלו:**

| חלופה | למה לא |
|---|---|
| **In-memory (ברירת המחדל של slowapi)** | נשבר עם יותר מ-worker אחד, ומתאפס בכל deploy. |
| **Postgres** | אפשרי, אבל כתיבה לדיסק על כל בקשה כדי לספור — בזבזני ומוסיף עומס למסד הראשי. |
| **Cloudflare / API Gateway rate limiting** | הפתרון הנכון בפרודקשן אמיתי — עוצר את הבקשה לפני שהיא בכלל מגיעה לאפליקציה. אבל אז הלוגיקה יוצאת מהקוד. |

**שאלת ראיון:** *"למה לא השתמשת ב-Redis גם ל-caching של תשובות?"*
**תשובה:** זו ההזדמנות הכי גדולה שלא מומשה. שאילתות שכר הן חוזרות מאוד ("כמה מרוויח DevOps") ו-embedding של אותו טקסט הוא דטרמיניסטי. cache על ה-embedding לבד היה חוסך קריאת רשת שלמה. cache על התשובה המלאה (עם TTL של שעות) היה מוריד latency לאפס וחוסך את מלוא העלות. זה ה-item הראשון ב-roadmap שלי.

### 6. SQLAlchemy 2.0 (ORM)

**מה זה:** ה-ORM של Python. אצלי בשימוש **מעורב** במכוון:
- **ORM** ל-CRUD פשוט: `db.add(post)`, `db.query(SalaryPost).count()`.
- **Raw SQL דרך `text()`** לשאילתת החיפוש ההיברידי.

**למה בחרתי:**
- הסינטקס החדש עם `Mapped[]` ו-`mapped_column` נותן type hints אמיתיים.
- `pgvector.sqlalchemy.Vector` משתלב ישירות כטיפוס עמודה.
- הבריחה ל-raw SQL היא הכרחית: אין ל-ORM דרך לבטא CTE עם `FULL OUTER JOIN`, `ROW_NUMBER() OVER`, ואופרטור `<=>` בצורה קריאה. כתיבת השאילתה הזו ב-ORM הייתה יוצרת קוד גרוע יותר מה-SQL עצמו.

**שאלת ראיון:** *"למה לא Alembic למיגרציות?"*
**תשובה:** חוסר אמיתי בפרויקט. כרגע אני משתמש ב-`Base.metadata.create_all()` שיוצר טבלאות אם אינן קיימות — אבל **לא מטפל בשינוי סכמה**. אם אוסיף עמודה למודל, המסד הקיים לא ישתנה. בפרודקשן זה חוסם. Alembic הוא הצעד הבא.

### 7. Pydantic + `pydantic-settings`

**מה זה:** ולידציה מבוססת type hints. שני שימושים:
1. **API schemas** — `QueryRequest`, `QueryResponse`, `IngestRequest`.
2. **Configuration** — `Settings(BaseSettings)` שקורא env vars.

**למה בחרתי:**
- **Fail fast על קונפיגורציה.** `database_url: str` בלי ערך ברירת מחדל אומר: אם משתנה הסביבה חסר, האפליקציה **מסרבת לעלות**. עדיף לקרוס באתחול מאשר לגלות את זה באמצע בקשה של משתמש.
- ולידציה של קלט חינם — `IngestRequest` עם `salary: float | None` דוחה מחרוזת ב-422 בלי שורת קוד.
- מקור אמת יחיד לתיעוד — אותה מחלקה מייצרת גם ולידציה וגם Swagger.

**שאלת ראיון:** *"מה קורה אם משתמש שולח `{"query": 123}`?"*
**תשובה:** Pydantic מחזיר 422 עם פירוט השדה שנכשל, לפני שהקוד שלי בכלל רץ.

### 8. slowapi (Rate Limiting)

**מה זה:** ספריית rate limiting ל-FastAPI, עטיפה של `limits`. מזוהה לפי IP (`get_remote_address`).

**למה בחרתי:** ה-endpoint שלי **עולה כסף אמיתי** לכל קריאה — 3 קריאות ל-OpenAI. בלי הגבלה, סקריפט אחד בלולאה יכול לרוקן את הארנק שלי. זו הגנה כלכלית, לא רק הגנה מעומס.

**המגבלות שנקבעו:** `/query` 10/דקה (יקר), `/ingest` 5/דקה (יקר + כותב למסד), `/stats` 30/דקה (זול).

**שאלת ראיון:** *"מגבלה לפי IP — מה החולשה?"*
**תשובה:** שתי חולשות. (1) **NAT** — כל משרד מאחורי IP אחד חולק מכסה. (2) **עקיפה** — proxy מסובב IP-ים שובר את זה מיידית. הפתרון הנכון הוא מגבלה לפי **זהות מאומתת** (user ID / API key), לא לפי כתובת רשת. וגם: מאחורי reverse proxy צריך לקרוא את `X-Forwarded-For`, אחרת כל הבקשות נראות כאילו הן מה-proxy.

### 9. Docker + Docker Compose

**מה זה:** שלושה services — `db` (image של `pgvector/pgvector:pg16`), `redis`, `api`.

**למה בחרתי:**
- **pgvector דורש התקנה של extension.** ה-image המוכן חוסך את זה לגמרי.
- **healthchecks + `depends_on: condition: service_healthy`** — ה-API לא עולה עד ש-Postgres באמת מוכן לקבל חיבורים. בלי זה יש race condition באתחול.
- **סביבה זהה בכל מקום** — `docker-compose up --build` ומישהו אחר מריץ את הפרויקט שלי.
- ה-volume `./backend/app:/app/app` נותן hot reload בפיתוח.

**שאלת ראיון:** *"מה הבעיה ב-docker-compose שלך לפרודקשן?"*
**תשובה:** כמה דברים: הסיסמאות מקודדות בקובץ (`postgres/postgres`), ה-volume mount של הקוד מתאים לפיתוח בלבד, אין resource limits, ו-`platform: linux/arm64` נעול ל-Mac שלי ולא ירוץ על שרת x86. לפרודקשן צריך קובץ compose נפרד או Kubernetes.

## חלק ב' — Frontend

### 10. Next.js 16 + React 19 + TypeScript

**למה בחרתי:**
- **ה-App Router נותן לי backend קטן בחינם.** זו הסיבה המרכזית — ראה סעיף 11.
- TypeScript מבטיח שה-interface של התשובה (`QueryResponse`) תואם למה שה-API מחזיר.
- React 19 עם hooks פשוטים (`useState`) — אין state management חיצוני כי אין צורך.

**חלופות:** Vite + React (קל יותר, אבל אין שכבת שרת), SvelteKit, או Jinja templates ישירות מ-FastAPI (הכי פשוט, אבל UI חלש).

### 11. שכבת ה-Proxy — התובנה הכי חשובה ב-frontend

**הבעיה:** בגרסה הראשונה הדפדפן קרא ישירות ל-backend עם `X-API-Key` מתוך `NEXT_PUBLIC_API_KEY`. **כל משתנה שמתחיל ב-`NEXT_PUBLIC_` נצרב לתוך ה-bundle של הדפדפן.** זה אומר שכל אחד שפותח DevTools רואה את המפתח הסודי שלי ויכול לשרוף לי את מכסת ה-OpenAI.

**הפתרון:** הוספת קפיצה:

```text
לפני:  דפדפן  ──(X-API-Key גלוי!)──>  FastAPI
אחרי:  דפדפן  ──(בלי סוד)──>  Next.js server  ──(X-API-Key)──>  FastAPI
```

ה-Route Handler רץ **בשרת Node**, ולכן יכול לקרוא `process.env.API_KEY` (בלי `NEXT_PUBLIC_`) שלעולם לא מגיע לדפדפן.

**שאלת ראיון:** *"אז עכשיו ה-proxy שלך פתוח לכולם — לא סתם העברת את הבעיה?"*
**תשובה:** נכון, וזה חשוב להודות בו. ה-API key מגן על ה-backend מפני קריאות ישירות מבחוץ, אבל ה-proxy עצמו הוא endpoint ציבורי. ההגנות עליו הן ה-rate limiting ו-CORS. הפתרון המלא דורש **אימות משתמשים** — session/JWT — כדי שהמכסה תהיה לפי משתמש ולא לפי IP.

> ⚠️ **הערה קריטית לפני הראיון:** בקוד הנוכחי הקבצים התחלפו. `frontend/app/api/query/route.ts` מכיל את **קוד הלקוח** (הפונקציה `querySalary`) במקום route handler, ו-`frontend/lib/api.ts` מכיל עדיין את הגרסה הישנה שקוראת ישירות ל-backend עם `NEXT_PUBLIC_API_KEY`. `page.tsx` מייבא מ-`@/lib/api`, כלומר בפועל שכבת ה-proxy **לא פעילה**. ראה מסמך 06 — חייבים לתקן לפני הראיון או לפחות לדעת להסביר את זה.

## 1. הבעיה: איך יודעים ש-RAG עובד?

תשובה של LLM "נשמעת טובה" תמיד. אי אפשר להעריך מערכת RAG לפי תחושה. צריך לפרק את ההערכה לשניים:

| מה בודקים | השאלה | מדדים |
|---|---|---|
| **Retrieval** | האם שלפתי את המסמכים הנכונים? | Hit Rate, MRR, NDCG |
| **Generation** | האם התשובה נאמנה למסמכים? | Faithfulness, Answer Relevance (RAGAS) |

**אני מדדתי retrieval בלבד.** זו החלטה מודעת ויש לה נימוק טוב: אם ה-retrieval מביא את המסמכים הלא נכונים, שום generation לא יציל את התשובה. **Retrieval הוא צוואר הבקבוק של האיכות.** בנוסף, retrieval ניתן למדידה אובייקטיבית מול ground truth, בעוד שהערכת generation דורשת LLM-as-judge שהוא בעצמו רועש.

## 2. סט הבדיקה — איך יצרתי ground truth בלי לתייג ידנית

קובץ: `app/rag/qa_generator.py`

**הבעיה:** כדי למדוד retrieval צריך זוגות `(שאלה, מסמכים רלוונטיים)`. תיוג ידני של מאות זוגות הוא עבודה של ימים.

**הפתרון — היפוך הכיוון:** במקום לכתוב שאלה ואז לחפש את המסמך המתאים, לוקחים מסמך קיים ומבקשים מ-GPT לייצר שאלה **שהמסמך הזה עונה עליה**. הקשר `(query, relevant_id)` ידוע בוודאות בבנייה.

```python
"""Given a salary post, generate ONE natural Hebrew question
that someone would ask, where this post would be a relevant answer.
Rules:
- Question must be in Hebrew
- Must sound like a real person asking
- Should NOT copy exact words from the post"""
```

**השורה הקריטית: "Should NOT copy exact words from the post".**

בלי ההנחיה הזו, GPT היה מייצר שאלה שמשכפלת את מילות הפוסט — וכל חיפוש מילות מפתח פרימיטיבי היה מוצא אותו. סט הבדיקה היה **triviali** וכל הגרסאות בהשוואה היו מקבלות 100%. ההנחיה כופה **פער לקסיקלי** בין השאלה למסמך, וזה בדיוק מה שמכריח את המערכת להשתמש בהבנה סמנטית.

`temperature=0.7` כאן (בניגוד ל-0 בשאר המקומות) — כדי לקבל גיוון בניסוחים.

**התוצאה:** 50 מקרי בדיקה ב-`generated_test_cases.json`. הרחבתי מ-5 ידניים ל-50 — עם 5 מקרים, טעות אחת משנה את הציון ב-20%, מה שהופך כל השוואה לחסרת משמעות.

### החולשה של השיטה — חייבים להודות בה

זו **synthetic data**, ויש לה שלוש בעיות:

1. **הטיה מעגלית.** אותה משפחת מודלים (`gpt-4o-mini`) יוצרת את השאלה *וגם* עושה את ה-expansion וה-reranking. יש חשש להתאמת-יתר לניסוחים שהמודל "אוהב".
2. **`relevant_ids` יחיד.** כל מקרה מסומן עם פוסט רלוונטי אחד. אבל אם יש במסד שלושה פוסטים על Frontend עם 4 שנים, השליפה של אחד מהאחרים היא **נכונה** — והמערכת נענשת עליה. **המדדים שלי הם lower bound: הביצועים האמיתיים טובים יותר ממה שהמספרים מראים.**
3. **שאלות סינתטיות ≠ שאלות אמיתיות.** משתמשים אמיתיים כותבים בשגיאות כתיב, קטוע, ובשפה מדוברת.

**התיקון:** לתייג ידנית 30-50 שאלות אמיתיות (מ-`query_logs`!) עם רשימת רלוונטיים מלאה. זה סט קטן אבל אמין.

## 3. המדדים — מה כל אחד אומר

קובץ: `app/rag/evaluator.py`

### 3.1 Hit Rate @ k

```python
def hit_rate_at_k(results, relevant_ids, k):
    top_k_ids = [r["id"] for r in results[:k]]
    return 1.0 if any(rid in top_k_ids for rid in relevant_ids) else 0.0
```

**מה זה:** האם לפחות מסמך רלוונטי אחד הופיע ב-k הראשונים. בינארי — 0 או 1.

**מה זה אומר:** "האם המידע הנכון בכלל הגיע ל-LLM?" זה מדד **recall** — הרף המינימלי. אם Hit Rate נמוך, ה-generation נידון לכישלון כי ה-context לא מכיל את התשובה.

**החולשה:** לא אכפת לו **איפה** בתוך ה-k. מקום 1 ומקום 3 מקבלים אותו ציון.

### 3.2 MRR — Mean Reciprocal Rank

```python
def reciprocal_rank(results, relevant_ids):
    for i, result in enumerate(results, 1):
        if result["id"] in relevant_ids:
            return 1.0 / i
    return 0.0
```

**מה זה:** 1/מיקום התוצאה הרלוונטית **הראשונה**. מקום 1 → 1.0, מקום 2 → 0.5, מקום 3 → 0.33, מקום 10 → 0.1.

**מה זה אומר:** "כמה גבוה הצלחתי לדחוף את התוצאה הנכונה?" זה מדד **precision-oriented**. חשוב במיוחד אצלי כי אני מעביר רק 3 פוסטים ל-generation — מיקום גבוה זה כל ההבדל.

**החולשה:** מסתכל רק על ההתאמה הראשונה ומתעלם משאר הרלוונטיים.

### 3.3 NDCG @ k — Normalized Discounted Cumulative Gain

```python
def dcg(hits):
    return sum(hit / math.log2(i + 2) for i, hit in enumerate(hits[:k]))

actual_dcg = dcg(hits)
ideal_dcg  = dcg(sorted(hits, reverse=True))
return actual_dcg / ideal_dcg
```

**פירוק שם המדד:**
- **Cumulative Gain** — סכום הרלוונטיות של התוצאות.
- **Discounted** — כל תוצאה מחולקת ב-`log2(position+1)`. הנחה לוגריתמית: תוצאה במקום 5 שווה פחות מתוצאה במקום 1, אבל לא באופן קיצוני.
- **Normalized** — מחלקים ב-DCG של הסידור המושלם, כדי לקבל ציון בין 0 ל-1 שניתן להשוואה בין שאילתות.

**מה זה אומר:** המדד המקיף ביותר — מתחשב **בכל** התוצאות הרלוונטיות ובמיקום המדויק של כל אחת.

**למה שלושתם ולא רק אחד?** כי הם מודדים דברים שונים: Hit Rate = "הצלחתי בכלל?", MRR = "כמה גבוה?", NDCG = "כמה טוב הסידור הכולל?". מדד יחיד מסתיר תמונות. למשל, Hit Rate גבוה עם MRR נמוך אומר: "אני מוצא את הדברים הנכונים אבל מדרג אותם רע" — וזו בעיה שרירנקר טוב פותר.

## 4. ה-Ablation Study — הכלי הכי חזק בפרויקט

קובץ: `app/ablation_study.py`

### מה זה Ablation

מתודולוגיה ממחקר ML: מסירים רכיב אחד בכל פעם ומודדים את הנזק. כך מוכיחים שכל רכיב **תורם**, במקום להניח שהוא עוזר.

### ארבע הגרסאות שהשוויתי

| # | גרסה | מה יש בה | מה מבודדים |
|---|---|---|---|
| 1 | **Semantic Only** | חיפוש וקטורי טהור | קו הבסיס (Naive RAG) |
| 2 | **Hybrid (no expansion)** | וקטורי + keyword על השאילתה הגולמית + RRF | תרומת **החיפוש ההיברידי** |
| 3 | **Hybrid + Query Expansion** | + GPT מפרק את השאילתה לקטגוריות | תרומת **הרחבת השאילתה** |
| 4 | **Full Pipeline** | + LLM reranking | תרומת **ה-reranking** |

הצטברות הדרגתית — ההפרש בין גרסה n ל-n+1 הוא בדיוק התרומה של הרכיב שנוסף.

**גרסה 2 היא החכמה ביותר בעיצוב הניסוי.** היא לא משתמשת ב-GPT expansion אלא מחפשת את **20 התווים הראשונים של השאילתה הגולמית** כ-LIKE pattern. זה מדמה "hybrid נאיבי" — כזה שכל אחד יבנה ביום הראשון. ההפרש בינה לגרסה 3 מוכיח שההשקעה בקריאת GPT נוספת משתלמת.

### הרצה

```bash
docker exec salary_intel_api python -m app.ablation_study
```

הפלט: טבלת סיכום עם Hit Rate, MRR ו-NDCG לכל ארבע הגרסאות, על 50 מקרי הבדיקה.

## 5. אופטימיזציית הביצועים — הסיפור המלא

### התהליך בארבעה שלבים

**שלב 1 — מדידה.** בניתי את `QueryTracker` שרושם latency לכל שלב בנפרד לתוך `query_logs`.

**שלב 2 — זיהוי.** השאילתה הראתה:
```text
retrieval:   5.0s   ← החשוד
reranking:   ~0.9s
generation:  ~1.0s
total:       6.9s
```
72% מהזמן בשלב אחד.

**שלב 3 — ניתוח.** פירקתי את ה-retrieval:
- `get_embedding()` — ~0.5s (קריאת רשת ל-OpenAI)
- `expand_query()` — ~1.4s (קריאת רשת ל-OpenAI)
- שאילתת SQL — מילישניות

שתי קריאות הרשת רצו **בטור**, ואין ביניהן תלות.

**שלב 4 — תיקון.**
```python
query_embedding, keywords = await asyncio.gather(
    get_embedding(query),
    expand_query(query)
)
```

### התוצאה

| מדד | לפני | אחרי | שינוי |
|---|---|---|---|
| retrieval ממוצע | 5.0s | 1.9s | **-62%** |
| total ממוצע | 6.9s | 5.1s | **-26%** |
| צוואר הבקבוק | retrieval | generation | **עבר** |

### מה למדתי מזה (התשובה לראיון)

1. **מדידה לפני אופטימיזציה.** בלי ה-tracker הייתי מנחש. יכולתי בקלות לבזבז יום על אינדוקס של Postgres — כשהשאילתה עצמה לקחה מילישניות.
2. **הרווח הגדול הוא לרוב במקביליות, לא באלגוריתם.** לא שיניתי שום לוגיקה. רק הפסקתי לחכות סתם.
3. **אופטימיזציה מזיזה את הבעיה.** צוואר הבקבוק החדש הוא ה-generation, וזה מכתיב את הצעד הבא: **streaming**. אם משדרים את התשובה טוקן-אחר-טוקן, ה-time-to-first-token יורד לכ-2 שניות והתחושה של המשתמש משתפרת דרמטית גם אם הזמן הכולל לא משתנה.

### מה עוד אפשר לשפר (סדר לפי תשואה)

| שיפור | חיסכון משוער | מאמץ |
|---|---|---|
| **Streaming של התשובה** | -3s ב-time-to-first-token | בינוני |
| **Cache של embeddings ב-Redis** | -0.5s בשאילתות חוזרות | קטן |
| **Cache של תשובות מלאות** | ~-5s (הכל) בשאילתות זהות | קטן |
| **ויתור על reranking בשאילתות פשוטות** | -0.9s | קטן |
| **אינדקס HNSW** | זניח היום, קריטי במיליון שורות | קטן |
| **מעבר ל-asyncpg** | מילישניות היום | בינוני |

**למה דווקא היא:** המילה `devops` לא מופיעה בשאילתה, אפילו לא אות אחת ממנה. השאלה כולה בעברית, והתשובה שמורה במסד תחת `role = "DevOps"` באנגלית. זהו המקרה שבו כל רכיב בצינור נאלץ להוכיח את עצמו.

## שלב 1 — `expand_query` בונה את הגשר

```json
{
  "role":     ["devops", "devops engineer"],
  "tech":     ["aws", "kubernetes"],
  "location": []
}
```

שלוש עבודות קרו כאן:

1. **תרגום** — "מהנדס תשתיות ענן" הפך ל-`devops`. בלי זה אין לענף המילולי שום מחרוזת לחפש.
2. **הרחבה** — המודל הוסיף `aws` ו-`kubernetes` שכלל לא נאמרו, כי הוא יודע שאלה הטכנולוגיות של התפקיד.
3. **סיווג** — כל טוקן שויך לקטגוריה. בלי הסיווג אין משקלים: אי אפשר לתת 3 נקודות לתפקיד ו-1 למיקום אם לא יודעים מה מהם מה.

`location` יצא ריק כי לא נשאל על מיקום — התנהגות נכונה, אין המצאת תנאי שלא ביקשו.

`temperature=0` כי זו משימת חילוץ, לא יצירה. אותה שאלה חייבת לתת אותם טוקנים בכל הרצה.

## שלב 2 — הענף המילולי: מדויק וצר

`_build_weighted_keyword_conditions` מייצר את ה-SQL הבא:

```sql
  CASE WHEN LOWER(role) LIKE '%devops%'            THEN 3 ELSE 0 END
+ CASE WHEN LOWER(role) LIKE '%devops engineer%'   THEN 3 ELSE 0 END
+ CASE WHEN LOWER(role) LIKE '%aws%'
       OR LOWER(company_stage) LIKE '%aws%'        THEN 2 ELSE 0 END
+ CASE WHEN LOWER(role) LIKE '%kubernetes%'
       OR LOWER(company_stage) LIKE '%kubernetes%' THEN 2 ELSE 0 END
```

התוצאה על חמשת הפוסטים:

| פוסט | role | הערכת התנאים | ניקוד |
|------|------|---------------|-------|
| **2** | `DevOps` | `'devops' LIKE '%devops%'` ✓ | **3** |
| 5 | `Backend Developer` | אין התאמה | 0 |
| 1 | `Frontend Developer` | אין התאמה | 0 |
| 3 | `Team Lead` | אין התאמה | 0 |
| 4 | `Data Scientist` | אין התאמה | 0 |

`WHERE (score) > 0` מסלק ארבעה מתוך חמישה. **הענף המילולי מחזיר פוסט אחד בלבד.**

שים לב ש-`'%devops engineer%'` לא התאים: בעמודה כתוב רק `"DevOps"`, ו-`LIKE` בודק הכלה — המחרוזת הארוכה אינה מוכלת בקצרה. זה לא מזיק כאן, כי הביטוי הקצר כבר תפס.

**רשימה מדורגת ב' (keyword):**

```
rank 1 → post 2   (score 3)
```

## שלב 4 — RRF מכריע

```
score = 1/(60 + rank_semantic) + 1/(60 + rank_keyword)
```

פוסט שאינו מופיע ברשימה מסוימת מקבל 0 על התרומה שלה (זהו ה-`COALESCE(..., 0)` בקוד).

| פוסט | חישוב | תוצאה | הופיע ב- |
|------|-------|-------|----------|
| **post 2** | `1/62 + 1/61` = 0.016129 + 0.016393 | **0.0325** | **שתי הרשימות** |
| post 5 | `1/61 + 0` | 0.0164 | סמנטי בלבד |
| post 1 | `1/63 + 0` | 0.0159 | סמנטי בלבד |
| post 3 | `1/64 + 0` | 0.0156 | סמנטי בלבד |

**פוסט 2 מקבל ציון כפול, כי הוא היחיד שקיבל תרומה משני הצדדים.** הוא היה רק *שני* בסמנטי, ובכל זאת עקף בגדול את פוסט 5 שהיה *ראשון* — כי לפוסט 5 יש תרומה אחת בלבד.

**זהו כל הרעיון של RRF בשורה אחת:** תרומה שנייה, ולו קטנה, שווה יותר מהפרש של מקום אחד בתוך רשימה בודדת.

## שלב 5 — הטבלה שסוגרת את הטיעון

מה כל גישה הייתה מעבירה ל-LLM:

| גישה | התוצאות | הבעיה |
|------|---------|-------|
| **סמנטי בלבד** | Backend, DevOps, Frontend | התשובה הנכונה **שנייה**. ההקשר מזוהם, וה-LLM עלול לצטט משכורת Backend |
| **מילולי בלבד** | DevOps | נכון — אבל **פוסט אחד**. אי אפשר לגזור טווח שכר מדגימה בודדת |
| **Hybrid + RRF** | **DevOps**, Backend, Frontend, Team Lead | התשובה הנכונה **ראשונה**, ועוד הקשר סביבה |

השורה האמצעית קריטית: ה-System Prompt מורה במפורש *"Give a salary range, not a single number"* — **המערכת זקוקה ליותר מפוסט אחד כדי לעמוד בהוראה של עצמה.**

זה בדיוק ההפרש בין `Hit Rate = 0.46` (סמנטי בלבד) ל-`0.88` (הצינור המלא) ב-ablation study.

## שלב 6 — מה קורה מיד אחרי

ארבעת המועמדים עוברים ל-`rerank_results`. ה-LLM קורא את כולם יחד מול השאלה, וסביר שיזרוק את Frontend ואת Team Lead כלא רלוונטיים.

**חלוקת התפקידים:** ה-RRF קבע את הסדר; ה-reranker זורק את מה שלא שייך; ה-generator מנסח מהשלושה שנותרו.

# חלק ב' — זיהום דאטה: הבעיה שהמערכת לא פותרת

## התרחיש

במסד יש שישה פוסטי DevOps:

```
30,000   29,000   31,000   30,500   32,000        ← חמישה מקובצים
15,000                                            ← אחד חריג
```

משתמש שואל "כמה מרוויח DevOps". **מה מונע מה-15,000 להיכנס לתשובה?**

**התשובה הכנה: כלום.**

---

## למה זה קורה — מעקב בקוד

```python
candidates     = await search_similar_posts(query, limit=10)        # generator.py:36
relevant_posts = await rerank_results(query, candidates, top_k=3)   # generator.py:60
context        = _build_context(relevant_posts)                     # generator.py:70
```

ה-LLM רואה **שלושה מספרים**. בפרומפט כתוב לו *"Give a salary range"* — אז עם שלושה מספרים, "טווח" הוא פשוט מינימום עד מקסימום. אם 15,000 באחד מהם, התשובה תהיה "15,000–31,000" במקום "29,000–32,000".

## למה ה-reranker לא מציל

ה-reranker מדרג לפי **רלוונטיות לשאלה**. ששת הפוסטים הם כולם DevOps — רלוונטיים באותה מידה בדיוק. אין לו קריטריון להעדיף אחד על השני, ולכן הבחירה בפועל שרירותית.

הוא **כן** רואה את המשכורת בפרומפט שלו:

```python
f"Post {i+1}: Role: {p['role']} | Salary: {p['salary']}₪ | ..."
```

אבל התפקיד שהוגדר לו הוא `"You rank salary posts by relevance to a question"` — **רלוונטיות, לא סבירות**. אף אחד לא ביקש ממנו לשפוט את המספר.

## הנקודה המרכזית: זו לא בעיית פרומפט

**גם LLM מושלם לא היה מזהה ש-15,000 חריג** — כי הוא רואה שלוש דגימות ואין לו מושג איך נראית ההתפלגות. **המידע פשוט לא נמצא בהקשר.** זו בעיה ארכיטקטונית, לא בעיית ניסוח.

## מה כן מסונן היום, ומה לא

`extractor.py` מסנן בכניסה:

```python
MIN_SALARY = 3000
MAX_SALARY = 300000
if salary < MIN_SALARY or salary > MAX_SALARY:
    salary = None
```

זה תופס **טעויות חילוץ** — כשה-LLM החזיר `62` במקום `62000`. הוא **לא** תופס מספר שנראה לגיטימי כמו 15,000, ולא אמור: 15,000 היא משכורת אמיתית לג'וניור.

## ולמה זה מחמיר ככל שיש יותר דאטה

זה החלק הלא-אינטואיטיבי. עם 820 פוסטי DevOps במסד, עדיין **רק 3** מגיעים ל-LLM — כלומר **0.37% מהנתונים**, שנבחרו לפי דמיון סמנטי שהוא כמעט אחיד ביניהם.

**יותר דאטה לא משפר את התשובה — הוא רק מגדיל את הסיכוי שהמדגם השרירותי יהיה לא מייצג.** זו לא סטטיסטיקה, זו אנקדוטה.

## הפתרון: להפריד את "מי" מ"כמה"

**RAG הוא הכלי הנכון לשאלה "מה אנשים אומרים על X". הוא הכלי הלא נכון לשאלה "כמה זה X".** למספר מצרפי יש כלי אחר: SQL.

> ⚠️ מה שמתואר להלן הוא **ארכיטקטורה מוצעת, לא מה שבנוי כיום.**

### הארכיטקטורה בשלושה שלבים

**שלב 1 — הגדרת קבוצת השוואה (cohort).** מ-820 שורות ל-64:

```sql
WHERE role ILIKE '%devops%'
  AND years_experience BETWEEN 5 AND 8
  AND post_date > NOW() - INTERVAL '12 months'
  AND salary IS NOT NULL
```

הסכימה **כבר תומכת בזה**: `years_experience`, `salary` ו-`post_date` קיימים ב-`models.py`. פשוט אף שאילתה לא משתמשת בהם לסינון.

**שלב 2 — אגרגציה ב-SQL:**

```sql
SELECT
  percentile_cont(0.25) WITHIN GROUP (ORDER BY salary) AS p25,
  percentile_cont(0.50) WITHIN GROUP (ORDER BY salary) AS median,
  percentile_cont(0.75) WITHIN GROUP (ORDER BY salary) AS p75,
  COUNT(*) AS n
FROM salary_posts
WHERE ...
```

**שלב 3 — ה-LLM רק מנסח.** הוא מקבל את הסטטיסטיקה ועוד 3 ציטוטים אמיתיים, ואינו מחשב דבר.

### למה חציון ולא ממוצע — עם המספרים

ששת פוסטי ה-DevOps מהתרחיש:

| מדד | תוצאה | מה קרה |
|-----|-------|--------|
| **ממוצע** | **27,917** | פוסט אחד גרר את התשובה **2,300₪ למטה** |
| **חציון** | **30,250** | הפוסט החריג נספר, אבל לא הזיז כלום |

החציון שואל "מי במקום האמצעי", לא "כמה סך הכול". **ערך קיצוני משנה את הסכום, אך לא את הסדר.** לכן אחוזונים עמידים לחריגים מעצם הגדרתם — בלי שום קוד לזיהוי חריגים.

## העיקרון החשוב ביותר: לא מוחקים חריגים, מגדירים קבוצה

ה-15,000 הוא כנראה לא זיהום. הוא כנראה ג'וניור עם שנה ניסיון, או משרה חלקית, או פוסט מלפני שלוש שנים.

**אם מוחקים אותו כי הוא נמוך, מטים את כל התוצאות כלפי מעלה** — ואז המערכת משקרת למשתמש בכיוון המסוכן ביותר עבורו: הוא ילך למשא ומתן עם ציפייה לא ריאלית ויפסיד את המשרה.

לכן במקום לסנן לפי **משכורת**, מסננים לפי **ניסיון, תפקיד ותאריך**. אם הקבוצה מוגדרת נכון, החריגים האמיתיים נשארים ספורים והאחוזונים בולעים אותם.

## שני שערי בטיחות נוספים

if n < 5:

עדיף להודות בחוסר מידע מאשר לתת מספר משלוש דגימות. זה כבר ברוח המערכת — ה-System Prompt אומר *"If there is not enough data — say so explicitly"* — פשוט אין היום מי שיאכוף זאת במספרים.

**2. להחזיר תמיד את `n` למשתמש.** "לפי 64 פוסטים" ו"לפי 3 פוסטים" הן שתי תשובות עם רמות ביטחון שונות לחלוטין. המשתמש זכאי לדעת באיזו מהן הוא מסתכל.

## איך המערכת יודעת שזו שאלת "כמה"?

הפתרון האלגנטי: **כבר רצה קריאת LLM לניתוח השאלה.** מוסיפים לה שדות:

```json
{
  "intent": "aggregate",
  "role": ["devops"],
  "experience_band": [5, 8],
  "tech": [],
  "location": []
}
```

- `intent: aggregate` → מסלול SQL (שאלות "כמה מרוויח X")
- `intent: opinion` → מסלול RAG כמו היום (שאלות "איך המעבר לפינטק")

**בלי latency נוסף**, כי זו אותה קריאה שכבר רצה במקביל ל-embedding.

ו-RAG לא נעלם — הוא עובר לתפקיד שהוא באמת טוב בו: **להביא 3 ציטוטים אמיתיים לצד המספר.** הסטטיסטיקה נותנת את הדיוק, הציטוטים נותנים את האמון.
